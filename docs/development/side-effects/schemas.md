# Schema write paths

[Documentation home](../../README.md)

Dated records from the [side-effects audit](README.md). These are rationale and failure analysis, not proof that the present code still has this shape.

## `schema-admin` (updated by `promote-schema-versions`, 2026-02-11)

- **Committed writes:** one DynamoDB write — the `konductor-schema-versions` record of the version's canonical content and SHA-256 hash, written after the registry write (`CreateSchema`/`UpdateSchema`) commits and before the response is built. The registry write remains the version's commit; the DynamoDB record is what makes replay and divergence detection possible.
- **Side effects:** the registry write itself, the record write, and `SchemaVersionPublished` on the control-plane bus (see the original record in [publishing.md](publishing.md) for the emission exception). A failed record write after a committed registry write returns an error to the caller; the retry hits the registry's no-change conflict and the conflict path completes the missing record (canonical comparison before recording, mismatched content → 409 with the registry's conflict).
- **Rubric:** (1) yes — the record carries domain, schema, environment, version, canonical content, hash, writer, and timestamp, everything a promotion consumer needs; (2) yes — the record hangs on the committed registry write, and a retried append that finds the registry already holding the version heals the record instead of minting a duplicate; (3) not applicable — no stream consumer acts on the versions table (no stream by design; promotion side effects ride the promotions table's stream); (4) yes — recording is synchronous read-your-write; (5) not applicable; (6) not applicable.
- **Failure walk:** registry write commits, record write fails → 5xx to the caller, whose retry hits the registry no-change conflict; the conflict path canonical-compares the registry content with the requested content, records it, and answers 200 with `duplicate: true` (append) or 409 (create). Registry write commits, record write fails, and the caller never retries → the versions table has a gap; promotion treats a target version without a record as divergence with a repair path via canonical `DescribeSchema` comparison. Registry write fails → nothing is recorded.
- **Decision:** STAY. **Rationale:** the write set is one atomic record put after the committed registry transition; the conflict self-heal makes the write idempotent on retries, and promotion reads tolerate a permanently missing record by flagging divergence.

## `schema-promotions` (added by `promote-schema-versions`, 2026-02-11)

- **Committed writes:** one DynamoDB write — the conditional `PROMOTION` head-item put in `konductor-schema-promotions` (`attribute_not_exists(pk) OR phase IN (COMPLETED, FAILED, CANCELLED)`). It carries the full work order: promotion id, domain, schema, source and target environments, requested version, phase `VALIDATING`, actor, timestamps, TTL.
- **Side effects:** none of its own. Reads (domain ACTIVE check, source-registry `DescribeSchema` for existence and the latest version) are synchronous gates; the replay workflow starts from the table stream's INSERT event, and every later effect hangs on a committed `UpdateItem` transition from the workflow.
- **Rubric:** (1) yes — the item is the complete input the stream consumer needs; (2) yes — the 202 follows the committed put, and a lost put means no 202; (3) yes — the consumer's `promote-{promotionId}` execution name is the idempotency key, and `ExecutionAlreadyExists` is treated as success; (4) yes — replay is asynchronous by design; (5) yes — the consumer is a small Lambda with a reserved concurrency of one shard's batch, documented under the promotions table in [data-model.md](../../reference/data-model.md); (6) not applicable — the POST body is not a durable envelope, hence the table.
- **Failure walk:** conditional check fails on a non-terminal head item → 409 with the active promotion id from `ReturnValuesOnConditionCheckFailure`; the caller tracks that id. Put fails transiently → 5xx; the caller retries and the condition keeps the retry safe. Crash after commit before response → the caller retries, gets 409 with the id, and follows the existing promotion.
- **Decision:** STAY. **Rationale:** exactly one synchronous commit; everything else is stream-driven.

## `schema-promotion-stream` (added by `promote-schema-versions`, 2026-02-11)

- **Committed writes:** none of its own — it consumes the promotions table's stream (event source filtered to `sk = PROMOTION`). Its two effects are `StartExecution` on INSERT of a VALIDATING head item and lifecycle events on MODIFY transitions (`SchemaPromotionStarted`/`Completed`/`Failed`).
- **Rubric:** (1) yes — the stream image carries the whole promotion, including the fields the workflow input and event payloads need; (2) yes — every effect hangs on a committed transition, never on the API response; (3) yes — the workflow start is idempotent on the `promote-{promotionId}` execution name (`ExecutionAlreadyExists` is success), and event emissions are at-least-once notifications that subscribers must already tolerate; (4) yes — replay and operator notification are both seconds-tolerant; (5) yes — the event source mapping sets bisect-on-error, bounded retries, a one-hour record age, and a dedicated failure queue with a depth alarm, so a poison record cannot block the shard past the 24-hour retention window; (6) yes — the stream record itself is the durable envelope.
- **Failure walk:** `StartExecution` throttled or the machine deleted → the batch retries, then bisects, then lands in the dedicated queue; redrive after fixing the cause. EventBridge rejects an entry → the consumer fails the batch (same retry path); duplicate emissions on redrive are harmless. A MODIFY whose transition is uninteresting (REPIN items are filtered upstream; REPLAYING→REPLAYING progress commits) is ignored.
- **Decision:** STAY. **Rationale:** this is the stream-driven side-effect pattern the rubric exists to promote — no synchronous fan-out anywhere in the promotion path.

## `schema-promotion-steps` (added by `promote-schema-versions`, 2026-02-11)

- **Committed writes:** three kinds, all conditional on the promotion id or the REPIN generation: replay's target version record (same shape as schema-admin's) plus the head item's `lastWrittenVersion` progress commit; widen's REPIN put (`attribute_not_exists(pk) OR generation = :old`); narrow's REPIN update (`generation = :gen AND widenedBy = :pid AND drainUntil <= :now`).
- **Side effects:** the replay's registry `UpdateSchema` (idempotent on `ClientTokenId = {promotionId}-v{N}`) precedes the record write — the same write-then-record order as schema-admin, self-healed by the no-change-conflict comparison path. No events are emitted; announcements are the workflow's and the stream consumer's jobs.
- **Rubric:** (1) yes — every committed item carries the full state a reader needs; (2) yes — progress and phase transitions commit before the workflow acts on them; (3) yes — plan short-circuits on existing records, replay treats the registry's no-change conflict as already-written after canonical comparison, widen short-circuits on its own `widenedBy`, narrow exits when superseded; (4) yes — the workflow is asynchronous by design; (5) not applicable — no stream consumer on this path; (6) yes — the Step Functions execution context is the durable envelope, and task retries converge because every step is idempotent.
- **Failure walk:** replay crash between registry write and record write → the retried task hits the no-change conflict, canonical-compares, and completes the record. Narrow loses the generation race → it re-reads, exits `narrowed: false`, and the newer flow owns the pattern. Widen loses three consecutive races → the task fails and the workflow records `REPLAY_FAILED` on the head item.
- **Decision:** ENVELOPE-DRIVEN. **Rationale:** the state machine is the envelope; conditional writes keyed by promotion id and generation make every retry converge.

## `schema-promotions` GET (added by `promote-schema-versions`, 2026-02-11)

- **Committed writes:** none. A consistent `GetItem` of the head item after the same authorization and domain gates as POST.
- **Decision:** STAY (read-only). **Rationale:** listed for completeness; the rubric covers write paths.
