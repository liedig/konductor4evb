# Decision Log

This document tracks architectural decisions, implemented changes, and deferred technical debt for the EventBridge Nexus project. It serves as a quick reference for understanding why the system is built the way it is.

## How to Use This Document

- **Implemented Decisions**: Review these when you need context on why something was built a certain way
- **Deferred Decisions**: Check here before starting new work - these are known issues that may affect your changes
- **Adding New Entries**: When archiving an OpenSpec change, add a row to the appropriate table

## Implemented Decisions

| Date       | Change ID                                    | Domain          | Summary                              | Key Decision                                                                                                                                                                                                                |
| ---------- | -------------------------------------------- | --------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2026-04-14 | domain-management-redesign | Domain Management | Single domain table, sync decide, workflow-owned events | Merged domains + registration requests into one table. Decide endpoint is synchronous (API GW → Lambda, no SQS). Approval workflow solely owns approval/rejection events and DDB status updates. All Step Functions use YAML + JSONata. SES notifications for approval requests and rejections. Update command is metadata-only (no status transitions). Status model: PENDING_APPROVAL → APPROVED → PROVISIONING → ACTIVE, with REJECTED, PROVISIONING_FAILED, INACTIVE. |
| 2026-04-14 | github-ci-templates | CI / DevEx | Gitflow branching, three-stage CI, toolchain pinning | Gitflow model with `develop` and `main` branches. CI workflow runs check → test → build sequentially (fail early on cheap checks). Rust toolchain pinned to stable via `rust-toolchain.toml`. `cargo-lambda` and `aws-sam-cli` installed via pip in CI. `Swatinem/rust-cache` for build caching. Makefile `check` target mirrors CI check job for local/CI parity. |
| 2026-04-14 | unit-test-foundation | Testing | Pure-function unit tests first, trait-based mocking deferred | Added inline `#[cfg(test)]` modules covering all pure/extractable logic: DomainStatus serde & Display, API response helpers, DynamoDB attribute helpers, domain name validation, and email body generation (approval & rejection). Trait-based AWS SDK mocking deferred to a future change — current tests cover deterministic logic without needing network calls. Email body `format!()` extracted into standalone functions to enable testing without SES. |
| 2026-04-16 | nexus-provisioning-enhancements | Cross-cutting | Rebrand to EventBridge Nexus, naming convention flip, saga rollback, account detection, RAM namespace sharing | **Rebrand**: Renamed from "EventBridge Control Plane" to "EventBridge Nexus" — reflects that it's an integration platform, not a control/data plane split. Event source prefix changed to `nexus.domain-management`, bus renamed to `nexus-bus`, trust role to `nexus-trust-role`. **Naming convention**: Flipped from `{env}-{org}-{domain}` to `{org}-{env}-{domain}` so resources group by org/domain rather than environment. Domain namespace defined as `{org}-{domain}` (environment-independent). **Saga rollback**: Provisioning workflow now implements compensating transactions — on failure, walks backwards through created resources and deletes them before marking PROVISIONING_FAILED. Best-effort cleanup with error tracking. **Account detection**: Provisioning workflow queries `by-owner` GSI to detect first-time accounts; approval notification email flags new accounts with trust-stack deployment advisory. **RAM sharing**: Domain namespaces stored as SSM Advanced Parameters at `/namespace/{domain}`, shared org-wide via AWS RAM resource share. Application accounts can discover domains locally without cross-account IAM. |
| 2026-04-16 | provisioning-event-cleanup | Provisioning | Remove intermediate event, rename outcome events to Provisioning | Removed `DomainCreationStarted` intermediate event — no consumers, and `PROVISIONING` domain status already signals that provisioning is underway. Renamed outcome events from `DomainCreationSucceeded/Failed` to `DomainProvisioningSucceeded/Failed` — the workflow provisions infrastructure, it doesn't create the domain (that happens during registration). Aligns with existing `PROVISIONING` / `PROVISIONING_FAILED` status values. Moved `isNewAccount` flag from the removed started event to the succeeded event payload. |
| 2026-04-17 | extract-notifications-stack | Notifications | SES identities extracted into optional sibling stack, conditional core deployment | SES email identity management moved from the Nexus core stack into a standalone `notifications-stack.yaml` template. Core stack makes `ApprovalFromEmail`/`ApprovalToEmail` optional (empty-string defaults) and guards notification Lambda functions, log groups, EventBridge rules, and IAM permissions behind a `NotificationsEnabled` CloudFormation condition. When notifications are disabled, the core stack deploys without SES resources; the approval workflow still runs (task-token-based) but operators must approve via direct API call. Same-region constraint: the notifications stack must deploy in the same region as the core stack because SES identities are regional. Design intent: decouple core deployment from SES verification lifecycle, enable testing without email, and leave the door open for alternate notification transports later. |
| 2026-04-18 | installation-guide | Documentation | Single installation doc, README becomes pointer | Created `docs/installation.md` as the single runnable end-to-end installation guide covering the three-stack deploy model (notifications, core, trust), prerequisites, smoke-test walkthrough, troubleshooting, and uninstall. Replaced the README's "Getting Started" section (which had duplicated and incomplete deploy steps) with a pointer to the installation guide. Rationale: a single doc eliminates drift between README and installation instructions; an operator following one doc from start to finish is less likely to miss a step. |
